For Pyth specifically, this is a very clean setup, and the answer is yes, you can update PriceInfoObjects on a sui-fork network — in most cases by submitting real Hermes VAAs the same way you would on mainnet. The reason is the property I mentioned earlier: VAA signatures are produced off-chain by Wormhole guardians and aren't bound to any particular destination chain. As long as the wormhole::State object that gets fetched into your fork carries the same guardian set Hermes is currently signing with — which it will if you forked recently — those VAAs verify byte-for-byte.
Concretely the flow is:

1. Start sui-fork at a recent mainnet checkpoint. The Pyth State, Wormhole State, and the PriceInfoObjects for whatever feeds you care about will be lazily fetched the first time your transaction references them.
2. Off-chain, fetch update data from hermes.pyth.network exactly as you would for mainnet (SuiPriceServiceConnection.getPriceFeedsUpdateData(priceIds)).
3. Build a PTB with SuiPythClient.updatePriceFeeds(tx, updateData, priceIds) pointed at the forked node's RPC, but using the mainnet Pyth and Wormhole state IDs (since that's the state your fork is mirroring). Submit it.
4. In the same PTB, call your protocol's function that consumes the now-fresh PriceInfoObject.

The replay-protection check (Pyth's stored last-consumed sequence number) is not an issue: Hermes always returns VAAs with monotonically increasing sequences, so a fresh fetch is always newer than whatever your fork captured at checkpoint time.
There are still two practical gotchas worth being explicit about because they're easy to hit on a fork specifically:
Clock drift versus VAA freshness. Sui's Clock is part of forked state, so it starts at whatever timestamp the source checkpoint had. If your fork is hours or days old, a freshly-pulled Hermes VAA has a timestamp far in the future relative to your Clock, while your consuming code's get_price_no_older_than(clock, max_age) is comparing against that stale Clock. The fix is whichever you prefer: re-fork from a fresh checkpoint, advance the fork's clock (epoch progression on sui-fork will move it forward), use a long max_age in tests, or — and this is where the new --forking-mode flag becomes genuinely useful — pull a historical price update from Hermes Benchmarks for a timestamp close to your fork's checkpoint, instead of a current one.
Guardian set rotation. Pyth/Wormhole occasionally rotate the guardian set via governance VAAs. If a rotation has happened since your fork's checkpoint, Hermes is now signing with the new set while your forked wormhole::State still trusts the old set. Either re-fork past the rotation, or submit the governance VAA that performs the rotation against your fork (the old guardians' signatures on that governance VAA will still verify against the old set, which is what your fork has).

This is the Sui equivalent of worm evm hijack that Wormhole ships for Anvil/Hardhat.

So the updated recommendation, given sui-fork exists: for any integration test that needs the real Pyth update path exercised end-to-end (VAA verification, fee payment, the actual PriceInfoObject mutation, your consuming function reading from it in the same PTB), sui-fork plus real Hermes data is now the right tool. Reserve the new_price_info_object_for_test helper on Pyth's main branch for pure unit tests of your business logic where you don't care about the verification path at all.
